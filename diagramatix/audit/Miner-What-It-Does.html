The Miner

Your systems already recorded what happened. Point the Miner at that record and it draws the process people actually followed — then shows you where it went wrong.

The idea

Nobody drew this diagram. The log did

Every workflow system, ticketing tool and ERP writes down what it did and when. That record is a description of the real process, and almost nobody reads it.

DiagramatixMINER reads it. Give it an export of events — a case, an activity, a timestamp — and it reconstructs the process as a BPMN diagram you can open and edit, plus the entity’s lifecycle as a state machine. Not a report about the process. The process.

Then it does the thing a picture alone cannot: it holds the real behaviour up against the process you say you follow, and counts the difference.

Getting started

From a spreadsheet to a process, in one sitting

1Drop in the log. CSV or TSV from any system, or the two interchange standards — XES (IEEE 1849) and OCEL 2.0, object-centric logs included.
2Say which column is which. Case, activity and timestamp are all that is required. The columns are guessed for you; you confirm.
3Check before you commit. A panel shows how many rows are usable, how many would be dropped, how the dates parsed, and warns when a column looks wrong — before anything is imported.
4Import, and the analysis is already done. Cases, events, activities, states, distinct variants, the span of the data — and the whole Insights workbench underneath.
If the log is missing something

Most real logs are thinner than the textbook. No column saying what state the entity ended in? Fill an activity→state table by hand, or pull it from a State Machine you already drew. No column saying who did the work? Fill the activity→team table from the lanes of your own BPMN diagram. The models you already have complete the log.

What it discovers

Three things, from one log

The process

  • A real BPMN diagram — every path people took, with gateways where the work genuinely branches and rejoins
  • Built straight from the data, no AI required, so it is a faithful mirror of the log
  • Optionally AI-curated into a cleaner reading — tidy labels, noise dropped — as a separate diagram
  • It is an ordinary Diagramatix diagram: open it, edit it, export it, simulate it

The lifecycle

  • The state machine of the thing flowing through — every state the invoice, order or ticket was actually in, and what moved it
  • Every transition carries how many cases took it
  • A guarantee that matters: a generated lifecycle shows every state in the log, never a tidied-up subset

The governance

  • If the log carries Control, Risk or Policy identifiers, they are mined too
  • For each control: how often it should have operated, how often it actually did, and the shortfall
  • Evidence a control is working, rather than a note saying it exists
Reality vs the rulebook

Conformance, and what it costs to be wrong

Discovery tells you what happened. Conformance tells you whether it was allowed.

You pick a reference — the lifecycle as it is meant to run. The Miner can create one for you from the mined behaviour, as a separate diagram you then edit into your rulebook: prune the moves that should never happen. Discovery never overwrites it.

Then it replays every real case against that reference and reports a single number — fitness, the share of cases that replay cleanly — plus each deviation, what it means and how many cases did it: a transition nobody documented, a state that should not exist, an entry or exit in the wrong place, a documented path nobody ever takes.

The deviations land back on the diagram. On the discovered state machine, every transition your reference disallows turns red.

The workbench

Seven ways to read the same run

Activities

  • One row per step: cases, occurrences, median time, total time
  • The team and the state each step produced — and an amber flag when a step is done by more than one team

Insights — the heat map

  • The discovered diagram with each step tinted by where the time goes
  • Colour by total time, by frequency, or by average time in step
  • The mined time and the owning team printed under each box, so the numbers sit on the picture

Variants

  • Every distinct way the process was actually run, most common first, with a cumulative share
  • Click one and its path lights up on the model; everything else fades
  • Tick two and it tells you exactly what differs

Cases

  • Every case, sortable by cycle time — the worst offenders first
  • Filter to one variant, click a case, see its path on the model
  • A live replay: work flowing over your discovered process, weighted by how often each path really happened

Outcomes

  • Set a case SLA and get the on-time / late split straight away
  • Which steps are over-represented in late cases, and by how much
  • Which whole paths are the late ones

Automation

  • For a task log — the UI steps inside one job — an automation score and a verdict
  • App ping-pong, rework, and the hours it would save
  • The strongest candidate routine as a step-by-step RPA specification you can hand to a build team, plus an SOP

Export

  • The whole analysis as Word, Excel or PDF — summary, bottlenecks, variant Pareto, outcomes
  • The log itself back out as XES or OCEL, for anyone who wants to check it in their own tool

Explain

  • Once the run is fully mined, a plain-English account of what was found — the real shape, the deviations and what they probably mean, the timing
  • Written from the computed figures, never instead of them
  • Works without AI too: the same summary, computed deterministically
Keeping it live

A log that refreshes itself

A mined process ages the day after you mine it. So a run can be attached to a live source: a webhook your system posts events to, or a folder it drops files into — Azure Blob storage or SharePoint.

New events arrive, the run rebuilds, and the discovered process, the lifecycle and the conformance check all re-run in place, on the diagrams you already have. The picture on the wall stays true without anyone re-importing anything.

Many things at once

When one case id isn’t enough

Real work rarely has one subject. An order has deliveries, which have items, which sit on invoices — and forcing all of that into a single case id is how process mining usually goes wrong.

Give the Miner an OCEL 2.0 log and it does the honest thing: it mines one lifecycle per object type, keeps them together as one study, and draws the object model that binds them — a Domain Diagram whose associations are weighted by how strongly the types actually interact, with a dashed line wherever two types clearly work together but nobody ever declared a relationship between them.

Fitting in

Where a mined process goes next

Into the Simulator

  • One button turns the mined run into a digital twin: fitted cycle-time distributions, the real arrival rate, gateway splits taken from observed frequencies, teams sized from how many cases each actually handled at once
  • Even the working calendar is mined — from the hours the work really happened in
  • So the to-be you test is a change to an as-is that was measured, not imagined

Into governance

  • Conformance findings become control effectiveness in the Risk & Control register
  • Runs roll up into org-wide Compliance Monitoring — the trend, per control, per project, per APQC category
  • A throwaway run can be excluded, so testing never pollutes the trend

Learning it

  • A catalog of worked examples — invoices, order-to-cash, an activity-only service-desk log, a task-mining routine, and a live streaming source
  • One click loads any of them into a fresh project with the run already mined, ready to discover, conform and simulate
  • Some ship several periods of the same process, so you can watch compliance decay
In short

The argument you cannot have without it

Process improvement usually stalls in the same place: everyone in the room has a different account of how the work is done, and none of them are wrong about their own part.

The Miner ends that conversation by producing the one version nobody has to take on trust — the one the systems recorded while everybody was busy.
