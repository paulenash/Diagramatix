What the Miner does, and what it should do next

A read of DiagramatixMINER as it stands from the user’s side of the screen — what it can be asked to do, the questions it already answers, and the eight additions that would turn a good discovery tool into something an operations team keeps coming back to.

7 September 2026 Read from the shipped code, not the roadmap Companion to “The Miner”, the external summary
Capability

What it does today

The Miner takes an event log, reconstructs the process and the entity lifecycle from it, checks both against a governed reference, and hands the result to the Simulator, the risk register and the reporting stack. Everything below is shipped and reachable from the console.

Getting the log in

Formats

  • CSV / TSV, with delimiter and header detection
  • XES (IEEE 1849) parsed to the same table
  • OCEL 2.0, JSON and XML, distinguished from XES by its object-model markers
  • Everything converges on one {headers, rows, mapping} pipeline — one importer, three formats

Mapping

  • Nine roles: case, activity, timestamp, state, resource, entity type, and Control / Risk / Policy ids
  • Only three are required; the rest are guessed and confirmable
  • No state column → an editable activity→state table, fillable from an existing State Machine
  • No resource column → an editable activity→team table, fillable from a BPMN’s lanes

Verifying before import

  • Usable vs dropped rows, distinct cases / activities / states, the detected timestamp format and the date span
  • Sample values per mapped role
  • Warnings for the classic mistakes: a single-valued case id, an unparseable timestamp, a free-text column mapped as state, mostly single-event cases
  • A full log viewer with filtering before you commit

What is mined

Compression and stats

  • Events → per-case traces → variants (distinct state/event sequences + frequency) — the bounded form everything downstream runs on
  • Headline stats: cases, events, activities, states, variants, span, rows dropped
  • A persisted per-case index (capped and strided at 50,000) so cases stay drillable without storing raw events

Timing

  • Per-activity sojourn samples, median and p90, and total time consumed — the true bottleneck signal
  • Per-edge transition times, directly-follows counts
  • Case cycle time: median, p90, min, max
  • Inter-arrival gaps, resource concurrency, and a 168-bucket hour-of-week activity histogram

Governance

  • Per control: expected (cases where a governed activity occurred), applied (cases where the control id was recorded), bypassed, effectiveness %
  • Risk and Policy traceability by distinct case count
  • Computed at import from transient traces — no per-event data is retained

Discovery

The process

  • Variants → directly-follows graph → a BPMN plan, with exclusive gateways at real splits and merges
  • Rendered by the same layout engine as every other BPMN, so the output is editable and simulatable, not a picture
  • Edge frequency badges carried onto the diagram
  • An optional AI-curated alternative that runs the mined paths through the app’s own BPMN rules and prompt, with mined frequencies re-annotated afterwards so calibration still works

The lifecycle

  • State sequences → a UML state machine, transitions labelled with the triggering activity and carrying case counts
  • A structural coverage reconcile runs after generation: any state, entry, transition or terminal the generator dropped is added back
  • That rule exists because a tidied-up reference makes every case touching a dropped state fail conformance — the AI path in particular

Object-centric

  • An OCEL log becomes a study: one run and one lifecycle per selected object type
  • A shared Domain Diagram — object types as classes, O2O relationships as associations, weighted by shared-event interaction strength
  • Dashed associations where two types synchronise behaviourally with no declared relationship
  • A study overview table showing each type’s progress: lifecycle, process, conformance

Conformance

The replay

  • Every variant replayed over a reference state machine, matched by label
  • Fitness = share of cases replaying cleanly
  • Five deviation kinds: undocumented transition, unknown state, unexpected entry, unexpected exit, dead transition — each with a case count and a severity

The reference

  • Created as a separate diagram (deterministic copy, or AI-curated) that discovery and refresh never overwrite
  • Chosen per run and persisted immediately, so the choice survives navigating away to edit it
  • The picker is scoped to the run’s own entity, and excludes the run’s discovered mirror
  • Disallowed transitions are flagged red on the discovered state machine

The Insights workbench

Activities and heat

  • Per-activity table: cases, occurrences, median, total time, teams and states, with multi-team and multi-state flagged
  • Heat over the discovered model by total time, frequency or average time — applied non-destructively, the saved diagram untouched
  • Mined time and dominant team captioned under each element

Variants and cases

  • Pareto list with share and cumulative share; click to isolate a path, tick two to diff them
  • Case list sorted by cycle time, filterable by variant, with per-case drill-down
  • A self-contained replay: work flowing over the discovered model, weighted by variant frequency
  • An expanded full-screen view for every tab

Outcomes and automation

  • A persisted case SLA, on-time / late split, and the activity and variant drivers of lateness ranked by lift
  • For task logs (auto-detected from the step vocabulary): automation score and verdict, ping-pong count, rework, an ROI estimate, and an exportable RPA spec and SOP

Getting it out

  • Analysis report as Word, Excel or server-rendered PDF
  • Log export as XES or OCEL at variant-level fidelity
  • “Explain results” — narrated by the model from computed figures, with a deterministic fallback when AI is off

Live sources

Connectors

  • Webhook push, authenticated by a minted key stored only as a SHA-256 hash and shown once
  • Azure Blob container by SAS URL, and SharePoint folder via the Graph picker
  • A rolling capped buffer with a watermark cursor, so re-polling a folder does not double-count

Refresh

  • Rebuilds the run from the buffer, then re-discovers and re-conforms in place on the existing diagrams
  • Only deterministic discovery re-runs automatically; AI curation stays manual because it costs quota
  • Manual refresh, plus scheduled polling per source

Where it connects

The Simulator

  • One click calibrates a digital twin: fitted service-time distributions (fixed or triangular), an exponential arrival fit, gateway branch probabilities from mined frequencies, per-task teams, and a working calendar derived from the hour-of-week histogram
  • Hands off to the Simulator and returns to the same Miner screen on exit

Risk & Control

  • A control names the deviation it guards; conformance then measures whether it operated
  • Two evidence sources — Control IDs on events (preferred) and conformance deviations
  • Org-wide Compliance Monitoring: effectiveness over time per control, per project, and by APQC PCF category, with a per-run include/exclude switch

The example catalog

  • Five published examples: AP invoice lifecycle, order-to-cash, an activity-only service-desk log, a task-mining routine, and a live polling source
  • Adopt loads one into a fresh project with the console pre-opened and the log staged
  • Admins can capture any run back into the catalog as a draft example
Worth naming

Two decisions carry more weight than any single feature. The first: discovery is deterministic by design. Every headline — the process, the lifecycle, the fitness, the timings — is computed, and AI is only ever a second, optional, clearly labelled curation on top. That is what makes a conformance number safe to put in front of an auditor.

The second: a discovered diagram is an ordinary diagram. It goes into the editor, the exporters, the Simulator and the risk register unchanged. Most mining tools end at a picture in a viewer; this one ends in the same place all the other work lives.

Extensions

What an operations team needs that isn’t there yet

The pattern across all eight: the Miner is very good at the first visit and thin on every visit after it. It discovers, it measures, it reports — and then the analyst has nowhere to go except back to the same three tabs. Several of these need no new mining at all; the numbers are already computed and persisted, and nothing renders them.

Now planned · 9 September 2026

Every extension and smaller item below is scheduled in Miner-Extensions-Plan.md, in the same folder. Nothing was dropped; two items are re-specified rather than built as written, and each says so where it appears.

Writing that plan meant reading the code a second time, which found four claims here that the code disproves and one thing this document does not mention at all — that the Miner’s routes were almost entirely ungated, so features sold by tier were being given away. The corrections are set beneath the arguments they affect, in amber. The original readings are left standing: they are part of the record.

The waiting between steps is measured, and never shown

Every run computes and stores per-edge metrics — how often each handover happened and the median time it took. Nothing in the UI reads them. The heat map colours boxes only, and the ranked bottleneck list is activities only. Put the heat on the arrows as well, and rank handovers alongside steps: the slowest transition, not just the slowest task.

In a real process most elapsed time is not inside a step, it is between them — sitting in someone’s queue, waiting for a batch run, bouncing back for more information. A tool that only colours the boxes tells you where the work is, not where the delay is, and those are usually different places. This is the single biggest gap between the Miner’s answers and the Simulator’s, and the data for it is already in the database.

Correction · 9 Sep 2026

“Render only” holds for the table, not for the arrows. There is no connector colour field in the diagram model — weight exists and is honoured only for the OCEL domain diagram’s associations. Colouring an arrow means changing the shared canvas renderer used by every diagram in the product. The plan splits it: the handover table and per-connector duration labels need no renderer change and carry the analysis; the coloured arrow is scoped separately, with a canvas regression bar.

You cannot slice the log

A run is all-or-nothing. There is no date filter, no team filter, no way to compare one region against another, and the importer keeps only the nine mapped roles — every other column in the file is discarded at parse time. So “how did Q2 compare with Q3”, “is the Melbourne team slower” and “do invoices over $10,000 take longer” are all unanswerable, even when the answer is sitting in the very spreadsheet that was uploaded.

Slicing is what turns a finding into a cause. “Approval is the bottleneck” is a fact; “approval is the bottleneck only for high-value cases, and only since June” is an action. Every other capability in the workbench — heat, variants, outcomes, conformance — becomes several times more useful the moment it can be pointed at a subset, and none of them need changing to gain it.

Two runs, side by side

The example catalog deliberately ships several periods of the same process so you can watch compliance decay — and there is no way to put two runs next to each other. Comparing means opening one, writing the numbers down, and opening the other. A comparison view would diff fitness, cycle time, variant mix, the bottleneck order, and per-activity time, and say which deviations are new since last time.

Nobody mines a process once. They mine it, change something, and mine it again — and the entire value of the second run is the difference from the first. The Simulator already establishes the pattern with its as-is / to-be assessment; the Miner, which has a much better claim to it because both sides are measured rather than modelled, has nothing.

From a deviation to the cases that caused it

Conformance reports a rule, a message and a case count. It never says which cases. The information exists — each stored case carries the variant it followed, and each variant carries the full state sequence that was replayed — so the offending case ids are one join away from what is already persisted. Today the audit trail stops at a number.

“Fourteen cases skipped the credit check” is where the conversation starts, not where it ends. Nobody can act on it, and no auditor can accept it, without the fourteen. This is the difference between a metric and evidence, and it is the same gap that makes the mined control-effectiveness figure hard to defend in a review.

Derivable today Drill-through Small Phase 5

Who hands work to whom

Resource is captured per event, a dominant team is computed per activity, and peak concurrency per resource is measured for the twin. From that the Miner could draw the standard resource views it currently has none of: a handover map between teams, workload distribution, and the pairs that pass work back and forth. Instead the resource dimension surfaces as one column in a table.

Process problems are usually organisational problems wearing a process costume. The step that takes four days often takes four days because it crosses three teams, and a handover map makes that visible in one picture in a way no per-activity table can. It is also the analysis business stakeholders recognise fastest, because it is about people rather than boxes.

Correction · 9 Sep 2026

Mined, but not kept. Resource is captured per event and then reduced to one dominant team per activity inside computeAnalytics; the per-resource counts are discarded. A handover map built from what is stored today would be an approximation, and it would mis-state precisely the multi-team activities that smaller item 03 flags amber. An exact map needs the per-case resource vector kept at import.

Rework and loops for ordinary processes, not just task logs

Rework detection and ping-pong counting exist and are good — but they only run when the log is recognised as a task log, and that recognition depends on activity labels literally beginning with “Switch to” or “Open” and containing “Copy” or “Paste”. A business process where “Credit check” is performed three times on the same case gets no rework figure at all, because its labels do not match a UI-step naming convention.

Repetition is the most universally actionable finding in process mining and the easiest for a business audience to accept — nobody argues that doing the same step four times is fine. The analysis is already written and is not task-specific in substance, only in how it is switched on. Generalising it costs little and gives every run a headline it currently lacks.

Correction · 9 Sep 2026

Half right, and the wrong half is dangerous. Rework detection really is label-agnostic — it counts repeats within a variant and widening it is deleting a condition. But ping-pong counting parses the labels (Switch to X, Open X, App: Step) and returns zero on a business log. Shipping the widened trigger without replacing it would put a confident wrong number on screen, which is worse than an absent one. The business analogue is team ping-pong over the resource sequence — a different function, over data the importer does not yet keep.

Volume over time, and whether the backlog is growing

Throughput is computed at import — cases started and cases completed, bucketed across the span of the log — persisted with the run, and never drawn. There is no arrivals chart, no completion chart, and no way to see that the process took in more work than it finished for six weeks running.

Cycle time tells you how long a case takes; throughput tells you whether you are keeping up. They fail independently, and the second is the one operations managers actually watch. A process can have perfectly healthy cycle times and still be quietly accumulating a backlog that will break it next quarter — and the Miner has already measured exactly that and thrown the chart away.

Watch it, rather than visit it

A live source ingests new events, rebuilds the run, re-discovers the process and re-runs conformance — entirely on its own, and entirely silently. If fitness falls from 94% to 71%, if a brand-new undocumented transition appears this week, if the late rate doubles, or if a source simply stops sending, nobody finds out until someone happens to open the console.

The live-source machinery is the most valuable thing in the feature and the least used, because it currently rewards nobody for turning it on. Thresholds plus a notification change what the product is: from a study you commission to a monitor that tells you when your process changed. Compliance Monitoring already stores the trend that an alarm would watch — it just has no alarm.

Smaller things, still worth doing

  • 01The case list shows sixty rows and cannot be exported. The full per-case index is stored; a CSV of it would let anyone check the analysis in a spreadsheet, which is exactly what a sceptical stakeholder asks for first.
  • 02“(sampled)” is shown without saying what it means. Above fifty thousand cases the stored per-case index is strided down. The headline figures stay exact, but the label does not say so, and a reader cannot tell which numbers to trust.
  • Correction · 9 Sep 2026

    Under-rated here as a labelling nicety. It is a correctness precondition for extension 2: the moment a filter exists, the stride turns every filtered figure into an estimate, and a filter selecting a rare value may resolve to almost nothing. The rule this document sets — every figure visibly filtered or visibly not — needs a third state it does not name: visibly estimated.

  • 03The multi-team flag is a dead end. An activity performed by more than one team is highlighted amber — and cannot be clicked to see the split. That flag is often the most interesting row in the table.
  • 04Discovery has frequency filtering that is never exposed. The discovery API already accepts an edge threshold that trims rare paths, and the console never sends one. A “simplify the map” slider is the standard remedy for the first reaction most people have to a discovered model, and the engine behind it is done.
  • 05Older runs have to be re-imported to gain new analysis. The empty-state message says so out loud. A “recompute” action on the run would avoid asking the user to find the original file again — which, months later, they often cannot.
  • Correction · 9 Sep 2026

    A recompute action cannot fix this for a manual run, because there is nothing to recompute from — the importer aggregates the raw events and discards them, by design. There are two honest answers, not one: a real recompute for live-source runs, whose windowed buffer still holds up to 100,000 raw rows, and a derived-only recompute for manual runs, which refuses by name anything needing per-event data. That constraint is why the plan front-loads storage: a field not captured at import is unavailable to that run forever.

  • 06A manual run cannot be appended to. Only live sources accumulate. Importing next month’s export means a whole new run, and therefore no continuity in a trend that only exists per run.
  • Correction · 9 Sep 2026

    Declined as written, and re-specified. Appending needs retained raw events, which do not exist and are not worth introducing for this. What the item actually asks for is continuity of trend, and a linked run series delivers that without the storage fork — the snapshot route already freezes a dated copy, it simply records no link back to the run it came from.

  • 07The automation ROI hard-codes its own key assumption. Hours saved is derived from a fixed seconds-per-step figure. Making it editable turns an illustrative number into one somebody is willing to sign.
  • 08The task SOP downloads as raw Markdown. The SOP generator already produces a styled Word document from a BPMN; the mined routine should go in the same door rather than out a second one.
  • 09Nothing masks values in an imported process log. The task-mining schema is explicit that values must be redacted, but a CSV import carries whatever is in the mapped columns — and case ids are frequently customer identifiers.
  • 10Connectors stop at webhook, Blob and SharePoint. A read-only database view or a REST endpoint is what most customers actually have, and asking them to build a webhook is asking for a project before they can see any value.
  • 11Conformance has no history of its own. Compliance Monitoring tracks controls over time across the org, but a single live run cannot show its own fitness moving — the one chart a process owner would check weekly.
  • Correction · 9 Sep 2026

    Not a smaller thing: a prerequisite of extension 8. No history, no alarm — you cannot alert on “fitness fell from 94% to 71%” when each refresh overwrites the run and no prior value was ever kept.

Not on this list, and it should have been · 9 September 2026

The Miner was sold by tier and enforced in three routes out of twenty-six. Discovery, conformance, calibration, validation, the AI explanation, both exporters, the snapshot, the OCEL importer and every live-source route carried a project-access check and no subscription check at all. The example gallery was the clearest case: the link was hidden for users without the entitlement while the API behind it answered anyone signed in. Hiding a door is not locking it.

Three further keys — Process Mining Examples, OCEL Support and Task Mining — were declared in the feature registry, shipped as availability rows to the production matrix, and enforced nowhere in the application. The Automation tab, the RPA specification and the as-actually-done SOP were being given away on every plan.

Fixed on 9 September 2026, ahead of the plan and as its own change, because it is a revenue defect rather than a renovation item. Twenty of the twenty-six routes now gate; the other six are exempted by name with a reason — the public webhook has no session to check, the cron poll runs as nobody, and four catalog routes are SuperAdmin-only. A test walks the route tree so the twenty-seventh route cannot be added without one.

Feasibility

Slicing the log: how it would work

The largest extension is also the one that changes the most existing screens, so it is worth being concrete about what it actually requires. The short version: one new field on the run, one filter component, and one predicate threaded through five tabs that already accept a filtered case list.

1Keep the columns we currently throw away. At import, every unmapped column becomes a case attribute, taken from the case’s first event. Attributes with too many distinct values to be a dimension are marked as such rather than dropped, so the user is told why they cannot filter on an invoice number.
2Store them on the per-case index. The case index already persists one row per case with its variant, timestamps and cycle time. Attributes belong on that row. It is capped and strided, which is the right trade already made once.
3One filter bar above the tabs. Date range, plus any attribute or team as a value picker. It produces a set of case indices and nothing else — a pure predicate over the stored index.
4Recompute the derived views from the filtered set. Activity metrics, variant frequencies, cycle statistics and the outcome split are all aggregations over cases, computed in the browser from data already loaded. No new server call, no re-mining.
Correction · 9 Sep 2026

True for variant frequencies, cycle statistics and the outcome split. Not true for activity metrics: the per-case index stores a case’s id, variant, start, end, cycle time and event count — and no per-event durations. Under this step as written, the heat map — the flagship of the workbench — is the one panel that would have to say “not filtered”. The plan therefore stores the durations at import first, in a phase of its own, before any filter is built.

5Leave conformance and discovery alone at first. Both replay variants rather than cases, so filtering them properly is a separate piece of work. Say so in the UI instead of pretending — a filter that silently does not apply to one panel is worse than one that says it does not.
Correction · 9 Sep 2026

The right instinct, the wrong pair. Conformance replay is a pure function of the variants and the reference, fitness is weighted by case count, and the filtered variant counts are just a histogram over the filtered case set — so filtering conformance is nearly free. The genuinely un-filterable one is discovery, and for a different reason: it emits a persisted diagram, so a filtered discovery has to be an explicit “discover from this slice” action creating a new diagram, never a live overlay.

The one thing to get right

Every figure in the workbench must be either visibly filtered or visibly not. The moment a heat map reflects the filter and a headline stat quietly does not, every number on the screen becomes unciteable — and this is a product whose entire claim is that its numbers can be cited. If a panel cannot honour the filter yet, it should say so on its face, not average the two.

In short

The mining is ahead of the reading

Very little of what follows is a mining problem. The engine already computes handover times, throughput curves, resource concurrency and a per-case index, and persists all of it on every run — three of the eight extensions above are render work over data sitting in the database today.

What is missing is the second visit. The Miner answers “what is happening” thoroughly and answers “what changed”, “for which cases” and “tell me when it moves” not at all. Those three questions are what turn a discovery exercise into something a team runs against its own process every month — and they are the difference between a feature people admire in a demo and one they keep open.

One word sharper · 9 Sep 2026

Reading the code again to write the plan moved this sentence slightly. “The mining is ahead of the reading” is exactly right for three of the eight. But three more are blocked on data the importer computes and then discards inside the same function — per-event durations, per-case resources, the columns nobody mapped. The sharper statement, and the one the plan is ordered around, is that the reading is ahead of the storing, and the storing only happens once. A field not kept at import is not missing until someone adds a recompute; it is gone.
