The Simulator — what it does, and how it does it

The companion to “The Simulator”. Part one is the machinery: where the numbers live, how a run is assembled and executed, what a Study and a Scenario actually are. Part two takes every question on the summary’s “What people use it for” table and answers it as a procedure — what you need before you start, how to build the study and its scenarios, what to press, and where the answer appears.

Part one · What it does

The diagram is the model

There is no second model to maintain. Every simulation parameter is a property of a BPMN element, edited in the diagram’s Properties → ◈ Simulation section or, for all of them at once, in the console’s Simulation Data panel. What each element carries:

ElementParametersNotes
Start / intermediate event (an arrival source)inter-arrival distribution, max arrivals, an operating-hours calendarThe calendar can carry a × multiplier per window — time-varying demand. Demand and staffing are different calendars: a 9–5 team queues overnight work; a 24/7 source keeps arriving.
Task / sub-processcycle time, optional setup and wait time, team, units required, needs these skills, repeats (loop / multi-instance)A task with no team inherits its swim-lane’s. A task marked as system-performed models automation.
Decision gateway → outgoing flowprobability % (must total 100) or a condition expression; one flow marked defaultInclusive and parallel gateways take their semantics from the notation.
Timer / delaydelay distribution; deadlines in working timeTwo working days is not forty-eight hours.
Boundary eventfire prob (chance it fires this execution), trigger (delay after scope start)Races the host task; interrupting or not per the notation.
Activity costa per-run activity chargeReported separately from staff cost.
Expanded subprocess / linked subprocess—An expanded subprocess simulates its inline body; a subprocess that links to another diagram is spliced in and run as part of the whole.

A duration is a distribution: fixed, uniform, triangular (min / mode / max), normal (truncated at zero), exponential, lognormal (the right-skewed shape service times actually have) or empirical — a list of observed values, resampled. Empirical values are written by calibration from a mined log or by a BPSim import, never typed.

The people

Teams, calendars and skills

Teams (Resources — people & automation)

  • A team is a shared resource pool: capacity, cost/hour, efficiency, a calendar, a queue discipline (First-come, Urgent first, Shortest first) and, for Urgent first, whether urgent work interrupts work in progress
  • Named members, each with the skills they hold; a task that needs these skills waits for someone who has them, and allocation prefers the least flexible person who qualifies
  • Org masters (OrgAdmin → simulation teams) are adopted into a project as its own copies; a team library can also be harvested from the diagrams’ lanes (match lanes)
  • Two tasks on two diagrams naming the same team compete for it — that is what a portfolio study measures

Calendars (Calendars — working hours)

  • A weekly pattern of open windows — presets Mon–Fri 9–5, 9–5 w/ lunch, 24/7, Demand: peak/off-peak — plus dated exceptions: holidays, a shutdown, absence
  • A team on a calendar is staffed at full capacity in open windows and zero otherwise; work in progress at close finishes, new work waits for the next window
  • Simulation time t = 0 is Monday 00:00. Utilisation is measured against staffed time

Skills

  • An organisation-wide master Skills list; people hold skills, tasks require them
  • Fill skills from an ArchiMate diagram reads the matrix a Business Architect already modelled — the same skills appear there as Capabilities
  • A scenario can give a person a skill or add a starter (teams[].members, merged by name) — the cross-training question
The engine

How a run is executed

Assemble. The study’s root diagrams are assembled once into a SimNetwork — hierarchy-aware (expanded subprocesses inline, event subprocesses as engine event subs, linked subprocesses spliced), with the scenario’s overrides applied on top of the diagram’s values and the team library resolved into resource pools.

Run. A discrete-event engine drives a binary-heap event calendar: tokens arrive per the source distributions, request units from resource pools, wait in queues ordered by the pool’s discipline, are pre-empted if the pool allows it, hold for working-time deadlines, and complete. Each replication uses a seed derived from the master seed (deriveSeed(seed, r)), so the same network and config give bit-identical results every time. The Warm-up is excluded from the statistics; queue lengths are sampled across the run when collectQueues is on.

Aggregate. N replications become mean / p5 / p50 / p95 ranges for throughput, flow time, cost per case and per-team utilisation and queue, with the per-replication means kept — that is what the significance test reads later. Run limits cap horizon × replications so a malformed study cannot wedge a server core.

Planned interventions are scheduled events in the run config, applied deterministically at time t: arrival (rate multiplier on a source), branchProb (a new probability on a flow), inject (a surge of tokens at a node), outage (a team’s capacity for a duration). The live Operator in the replay does the same thing by hand, forking the timeline from the current instant.

The objects

Study, Scenario, Run

ObjectHoldsWhere
Studya name, one or more Root diagrams (a portfolio shares its team pools), its business-case inputsStudies & Scenarios panel · /projects/:id/simulation/studies
Scenariorun config — time unit, Horizon, Warm-up, Replications, Seed, planned interventions; a sparse override set — element times / team / units / skills, flow probabilities, team capacity / discipline / members; a BASELINE flag; for an As-is / To-be pair, which diagram variant it runsone row per scenario under the study; Duplicate copies one; Create pair makes As-is and To-be

Everything analytical is a pure function over stored runs: significance (Welch over per-replication means), sweep (a lever across a range, knee = maximum distance from the chord), sensitivity (every parameter ±20%, 2N+1 runs, sorted into a tornado), validate (simulated vs observed flow-time distributions), the facts/ modules behind the business case, the assessment and next steps, and runTrend. Because they read stored metrics, they can be re-run without re-simulating.

In and out

Interchange

BPSim

  • Interchange — BPSim export / import: the OMG/WfMC standard, both directions, cost included (CostParameters/FixedCost)
  • A BPSim import can carry batching and empirical distributions the editor does not type

Packages

  • Export a study as a .dgxsim.json bundle — diagrams, teams, calendars, scenarios — and adopt it elsewhere
  • The example gallery is the same package format; Save as example (admin) captures a study into it

From the Miner

  • ▶ Calibrate & simulate writes fitted durations, arrivals, branch odds, teams and a mined calendar onto the discovered BPMN and creates a study with an As-mined baseline
  • Diagram values already documented can be copied into the model (use diagram values) instead of invented
Part two · How it does it

Before any of them: the setup every study needs

Every guide below starts from this state. Do it once per process.

Start with
  1. A BPMN diagram of the process in a project: start event → tasks → gateways → end event, tasks in the lanes of the teams that do them.
  2. Rough numbers — how long each step takes, how often work arrives, how decisions split — or a mined event log, which supplies them.
Build
  1. Open the diagram and click ◈ Simulator on the toolbar (also reachable from a Project or the Dashboard, which then asks which process).
  2. Open Simulation Data. Every element’s parameters are in one table; fill the gaps inline, or press ⚙ Fill missing simulation data for starting values (it never overwrites what you typed, and filled numbers look different from measured ones). If the diagram already documents effort and frequency, use diagram values instead.
  3. Open Teams. Add each team (New team, e.g. Assessors) with its Capacity; set Cost/hour if cost matters. Or adopt the organisation’s masters, or match the diagram’s lanes.
  4. Open Calendars. Add Business hours from a preset and assign it to each human team in the Teams panel’s Calendar column. Leave automation and arrival sources on 24/7 unless demand itself has hours.
  5. Open Studies & Scenarios. Create a study (new study (e.g. Q3 workload)), add the diagram under Root diagrams, and create the first scenario. The first scenario is the BASELINE.
  6. On the scenario set the run config: time unit, Horizon (long enough for several hundred cases), Warm-up (leave it — it is chosen for you), Replications (10–30), Seed (any fixed number).
  7. Press ▶ Run. The readiness check runs first and separates what would mislead you from what is merely assumed; Run anyway is available, Complete the simulation setup takes you to the gap.
Read
  1. The compact summary: throughput, flow time p50 / p95, the top bottleneck team and its utilisation.
  2. ▸ full results for the report; Heatmap, Run / Replay, the token trace, and — once there are two scenarios — Compare.
The guides

What people use it for, step by step

1 · Where does it actually get stuck?

Aim: the task where work waits longest — often not the one everybody blames.

Start with
  1. The setup above, with real or filled durations and a capacity per team.
Build
  1. One study, one root, the baseline scenario. Replications 10 is enough for a first look.
  2. Turn collectQueues on (it is the default) so queue lengths are sampled through the run, not only at the end.
Run and read
  1. ▶ Run, then Heatmap: your own diagram with each task tinted by the wait before service; the brightest box is ringed. Waiting inside a collapsed subprocess shows on its box.
  2. ▸ full results → Busiest tasks — wait before service and Teams — utilisation & queue, ranked. A team near 100% of staffed time with a growing queue is the constraint.
  3. Run / Replay to show it: tokens pile up where the queue is. Pause at the pile-up and use the Operator to add a person — the timeline forks and you watch whether the pile clears.
Watch out for
  1. A bottleneck that is a calendar, not a person: a 9–5 team looks saturated if the source runs 24/7. That is real, but the remedy is hours, not headcount.

2 · How many people do we need?

Aim: the headcount at which the promise you want to make starts holding — a curve, not a point.

Start with
  1. The setup, plus the promise stated as a number: “p95 flow time under 3 days” or “utilisation under 85%”.
Build
  1. On the baseline scenario open ▸ Sweep a number. Choose the lever — the team’s capacity — and the range (from 1 to 12) and the number of points. Each point is a full Monte-Carlo run, bounded by the sweep limit.
  2. Choose what the curve measures: Near-worst case (p95), Typical case (p50), Cases completed or Cost per case.
Run and read
  1. Run the sweep. The response curve is drawn with the knee marked — the point of maximum distance from the chord, where one more person stops buying much. On a flat curve it says so rather than inventing an elbow.
  2. Read across from your promise to the curve: the first capacity at which the objective is met is the answer; the knee tells you whether going further is worth it.
  3. To keep the answer, Duplicate the baseline into a scenario at that capacity (override the team’s Capacity) and run it, so Compare can show it against the baseline later. Or open Suggested next steps — it proposes that scenario and creates it for you.
Watch out for
  1. Sweep one lever at a time. Two levers moving together give a curve nobody can read.

3 · Is the redesign worth doing?

Aim: both versions side by side, with the difference in time and in cost.

Start with
  1. The as-is diagram set up as above, and a to-be diagram — the redesign drawn as its own BPMN, with the same team names where the same people do the work.
Build
  1. In Studies & Scenarios use Create pair: it makes an As-is and a To-be scenario in one study, each pointing at its diagram variant, sharing the team library.
  2. Give both the same run config — horizon, replications, seed — so the only difference is the design.
  3. If the redesign also changes staffing, put that in the To-be scenario’s overrides, not in the diagram.
Run and read
  1. Run both. Open Compare: deltas vs the baseline for throughput, flow time p50 / p95, cost per case, FTE freed — and the plain-language verdict (“% faster, $/case”).
  2. Then ask guide 11 — is the difference real? — before anyone quotes the percentage.
  3. For the money, guide 13.

4 · What if we changed the policy?

Aim: what auto-approving, re-routing or re-prioritising would do, before anyone lives through it.

Start with
  1. The setup, and the policy expressed as one of three things: a decision that splits differently, a task that a system does instead of a person, or a queue that is served in a different order.
Build
  1. Duplicate the baseline scenario and name it for the policy (new scenario (e.g. auto-approve under $5k)).
  2. Auto-approve: override the gateway’s outgoing flow probabilities (gateway → target rows) so more work takes the fast branch, or mark the approval task as system-performed — “what if we automated this task?” is one click on the task.
  3. Re-route: override the task’s team to the team that would now do it.
  4. Re-prioritise: override the team’s queue discipline to Urgent first (and tick interrupts if urgent work should pre-empt) or Shortest first.
Run and read
  1. Run and Compare against the baseline. Watch the per-segment service level as well as the pooled one when the policy is a priority rule — the pooled figure can improve while the standard segment is starved.

5 · Can we survive month-end?

Aim: what a tripled volume does to the backlog, and how long it takes to clear.

Start with
  1. The setup, plus when the peak starts, how big it is, and how long it lasts.
Build
  1. Duplicate the baseline into Month-end.
  2. Under Planned interventions add an arrival intervention: target the start event, value 3 (a rate multiplier), at time t of the peak, with the peak’s duration. Or, for a backlog that lands at once, an inject of N tokens at t.
  3. Alternatively model a recurring pattern with a Demand: peak/off-peak calendar on the source, its peak windows carrying a × multiplier.
  4. Make the horizon long enough to see the queue clear after the peak.
Run and read
  1. Run. In Run / Replay the surge visibly banks up and drains; the queue-length series in the report shows the peak and the time to return to normal.
  2. Add a second scenario with Surge staffing (peak week): a team-capacity override plus an outage intervention in reverse is not needed — simply raise Capacity for that scenario — and Compare the clearance time.

6 · What happens if two people are off?

Aim: how far behind you are by Friday.

Start with
  1. The setup with the team’s true capacity and calendar.
Build
  1. Duplicate the baseline into Two off.
  2. Either add an outage intervention on the team — value = capacity during the outage (capacity minus 2), at t = the start of the absence, duration = its length — or, for planned leave, add dated absence to the team’s calendar.
  3. For a whole-site closure — a bank holiday, a shutdown — put the dates on the calendar instead; arrivals keep landing and queue.
Run and read
  1. Run and Compare: the queue at the end of the week and the flow-time p95 tell you how far behind; the replay shows the pile building by day.
  2. Try a third scenario with cross-cover — give a named person from another team the missing skill (guide 14) — and see whether it holds.

7 · What can we promise?

Aim: the turnaround you would hit ninety-five times in a hundred — not the average, which you miss half the time.

Start with
  1. The setup with measured (or mined) durations. A promise built on filled-in guesses is a guess.
Build
  1. The baseline scenario with Replications raised to 30 or more — the p95 is a tail figure and needs the samples.
  2. A horizon long enough for the queues to reach steady state after the warm-up.
Run and read
  1. Run. Read Near worst (p95) in the summary and the flow-time histogram in the full report; that is the promise, in working time.
  2. If the promise is for a segment (urgent cases), read the per-segment service level — guide 15.
  3. Keep the run: Name this run and pin it as the baseline so later runs report their drift from it.
Watch out for
  1. Elapsed versus working time: a p95 of two working days is four calendar days over a weekend. Say which one you are promising.

8 · What does a case cost us?

Aim: staff time and cost per case, and where it goes.

Start with
  1. The setup plus Cost/hour on every team, and any per-run activity charge on tasks with a non-time cost (a credit check fee, a courier).
Build
  1. The baseline scenario as is. Cost needs no separate configuration once the rates are on the teams.
Run and read
  1. Run. Cost / case and Total cost are in the summary; the report’s Cost of doing the work breaks it down by team and separates activity charges from staff cost, because the two have different remedies.
  2. For rework, set the task’s rework percentage and read the cost of rework as its own line.

9 · Why does a two-hour job take two days?

Aim: the gap between working time and elapsed time, measured.

Start with
  1. The setup with calendars on the human teams and the arrival source left on 24/7.
Build
  1. The baseline scenario. If you suspect hand-offs, make sure each task’s team is the team that really does it, not the lane’s default.
Run and read
  1. Run. The token trace (▸ full results → trace) lists every case with the time spent in each step — service time against wait. Sort by wait.
  2. The gap is the waits: for a free person, for the next shift, for a batch cut-off. The heatmap shows which of the three it is by where the colour sits.
  3. Export the trace to a spreadsheet for anyone who wants to check the arithmetic rather than take it.

10 · Which process is starving the others?

Aim: contention between processes drawing on the same team.

Start with
  1. Two or more BPMN diagrams whose tasks name the same team where the same people do the work, and one consistent time unit across them.
Build
  1. One study with every diagram under Root diagrams. The engine assembles them into a single run sharing one capacity pool per team.
  2. A baseline scenario, then one scenario per remedy: more capacity on the shared team; a priority discipline so one process’s work goes first; a dedicated team for the starved process.
Run and read
  1. Run the baseline. The team table shows the shared team’s utilisation and queue; the per-process throughput shows who is starved.
  2. Compare the remedies. A priority rule moves the starvation rather than removing it — read both processes’ p95, not one.

11 · Is the improvement real, or noise?

Aim: a confidence interval on the difference, and how many more runs would settle it.

Start with
  1. Two scenarios in one study that have both been run — typically the baseline and the change from guides 2–6.
Build
  1. Nothing new. The test reads the per-replication means every run already stores.
Run and read
  1. Open Compare. The verdict line reports the difference in flow time as a confidence interval from a Welch test over the replications.
  2. If the interval spans zero it says the difference is not (yet) real and offers Run N replications — the number that would settle it. Press it; both sides re-run with that many replications and the verdict updates to ✓ real or stays honest.
  3. Quote the interval, not the point: “between 9% and 21% faster” survives a meeting; “17% faster” does not.

12 · Which assumption matters most?

Aim: the tornado — every input pushed ±20% and ranked by how far the answer moves.

Start with
  1. A scenario that has been run, and a sense of which inputs were measured and which were guessed.
Build
  1. On the scenario open ▸ Which assumption is load-bearing? (the tornado). Choose what it measures. It enumerates every parameter — each duration, arrival rate, branch probability, capacity — and runs two full simulations per parameter, one at −20% and one at +20%: this takes longer than a sweep.
Run and read
  1. The bars are sorted widest first. The top bars are the load-bearing assumptions; if one of them was a guess, that is where better data is worth buying. A guess at the bottom is safe to leave.
  2. Feed the top bar into guide 2 (sweep it properly) or into the Miner (measure it from a log).

13 · When does it pay back?

Aim: cost per case before and after, the one-off cost, and the payback month.

Start with
  1. An as-is and a to-be scenario both run (guide 3), and three business inputs: Cases a year, the One-off cost of the change, and any recurring Per case cost it adds.
Build
  1. Open Business case on the study. Enter the three inputs; they are stored on the study, not on a scenario.
  2. Pick the before and after scenarios (the baseline and the change).
Run and read
  1. The panel narrates cost per case before and after, the annual saving, the one-off cost and the payback month. A missing input is reported as missing — it is never treated as zero.
  2. Export it as Word, Excel or PDF; the document carries the significance verdict from guide 11 so the saving is stated with its interval.
Watch out for
  1. A business case cannot be made from a scenario that never ran — the panel refuses rather than reporting a zero.

14 · What if we trained someone?

Aim: a scenario that gives a person a skill, or adds a new starter, and what it does to the queue.

Start with
  1. Teams with named members and their skills, and tasks that declare needs these skills. Fill the matrix by hand in the Teams panel, or Fill skills from the ArchiMate diagram where it is already modelled.
Build
  1. Run the baseline first: with skills declared, a task waits for a qualified person, and the queue in front of the scarce skill is the finding.
  2. Duplicate into Cross-train. In the scenario’s team override, add a person by name with the new skill (an existing name gains the skill; a new name is a starter). Members are merged by name, so naming one person never deletes the rest of the team.
  3. Optionally a third scenario: the same relief by hiring — capacity +1 on the team that holds the skill — to compare training against hiring.
Run and read
  1. Run and Compare. Read the scarce-skill task’s wait and the p95 across the three. Allocation prefers the least flexible qualified person, so the cross-trained person is used only when the specialist is busy — which is what a manager would do.
  2. Guide 13 for whether the training cost pays back.

15 · Is the promise holding for the urgent ones?

Aim: service level per segment, not just pooled — and a queue discipline that puts them first.

Start with
  1. Work that arrives in two classes — urgent and standard — modelled as two arrival sources or a gateway that splits by class, each class with its own promise.
Build
  1. Baseline: the team on First-come. Run it and read the service level per segment in the report: a pooled p95 can look healthy while the urgent segment misses entirely.
  2. Duplicate into Urgent first: override the team’s discipline. Tick interrupts if an urgent arrival should pre-empt standard work in progress (the interrupted case resumes with the work already done).
  3. A third scenario with Shortest first if the classes differ mainly in size.
Run and read
  1. Compare the urgent and standard p95 side by side. The right discipline is the one under which both promises hold, not the one with the best pooled figure.

16 · Does the model resemble reality?

Aim: the simulated flow-time distribution against the real one, with an agreement figure — out-of-sample for a mined twin.

Start with
  1. A real event log of the process, in the Miner. This guide runs through the Miner console because the comparison needs the log.
Build
  1. Import the log and, on the import screen, Hold back the most recent share of cases (say 20%) — the twin will be fitted on the earlier cases and tested on these.
  2. Discover the process, then ▶ Calibrate & simulate: the study with its As-mined baseline scenario is created and the Simulator opens on it.
  3. Run the baseline.
Run and read
  1. Back in the Miner, open Does the model match reality? The simulated flow-time distribution is laid over the held-back cases’ real one, with a p50 / p90 / p95 table and an agreement figure. Out-of-sample, because those cases were never fitted on.
  2. If the agreement is poor, the tornado (guide 12) says which fitted assumption to distrust; a re-mined log later re-tests the same twin. A refreshed live run marks the twin stale rather than silently re-calibrating it.
After any of them

Open Suggested next steps on the study. It reads the runs you have just made, ranks what to try next with the evidence for each — where every improvement so far came from, which lever never moved the answer, what has not been tried — and can create the scenario for you. What would sharpen this lists the inputs worth measuring. Negative results are reported as plainly as promising ones.
