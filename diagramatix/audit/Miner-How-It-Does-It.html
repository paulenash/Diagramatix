The Miner — what it does, and how it does it

The companion to “The Miner”. Part one is the machinery: how a log gets in and what is kept, how discovery and conformance work, what a run, a series and a live source are. Part two takes every question on the summary’s “What people use it for” table and answers it as a procedure — what you need before you start, what to import and map, which reference or slice to build, what to press, and where the answer appears.

Version 3.1 · 14 September 2026 · product 2.11 · read from the shipped code

Part one · What it does

Getting the log in, and what is kept

The importer is the only moment the raw truth exists, so it keeps more than it used to. Import an event log accepts CSV / TSV, Excel workbooks, XES (IEEE 1849) and OCEL 2.0 / 1.0. A wide export — one row per case, a column per milestone — is detected and offered for unpivoting (“No, it is already one row per event” declines). Several systems’ extracts of the same cases are merged into one lifecycle with Add this export to a merge, an optional Id crosswalk file joining their case ids, and the cross-system hand-off measured at the join.

MappingMeaningNotes
Case ID *the thing that flows — invoice number, application idcan be masked when it is really a customer number
Activity *what happened—
Timestamp *when — ISO or epoch; rows are ordered by it within a caseper-event timings are kept, so between-step gaps are exact
Statethe entity’s resulting statewhat conformance replays; can be filled from a State Machine you drew (enrich)
Resourcewho or what did the workper-event resources are kept — the handover map needs them; can be filled from the BPMN’s lanes
Control IDControl / Risk / Policy ids carried on eventsmined into governance aggregates for the Risk & Control register
any other columnkept if you tick ita kept column becomes a slice dimension; any column can be masked on import

Before the import commits, a verification panel shows usable and dropped rows, the timestamp format and range, and sample values; the whole parsed log opens full-screen and filterable. Hold back the most recent share of cases sets aside an out-of-sample test set for a twin. A run then stores the traces and variants, a per-case index (strided above fifty thousand cases, and every figure built on it says estimated), the analytics — activities, edges, team flow, handovers, outcomes, throughput — the governance aggregates, and the raw events, which is what makes slicing exact and recompute honest.

Discovery and conformance

Two diagrams, one rulebook

Discover the process

  • A directly-follows graph becomes a real BPMN: tasks in a pool, an exclusive gateway where work fans out, merges where it rejoins, loops as they fall out, start and end added
  • A Detail slider drops the rarest paths (0 draws every path the log contains); connectors carry how often each step was taken, and the median gap
  • AI-curate optionally produces a cleaner reading as a separate diagram; the faithful mirror is never overwritten
  • Discovery from a slice is named after the slice and never becomes the run’s own model

Discover the state machine

  • The entity’s lifecycle from the state column: observed states as nodes, observed moves as transitions labelled with their activity, each with its case count
  • Coverage guaranteed: every state in the log appears, never a tidied subset
  • Promote it, edit it, or Create draft reference from it when the project has none

Conformance vs the reference

  • Pick a reference State Machine (only ones describing the same entity are offered); every case’s state sequence is replayed against it by label
  • Fitness = the share of cases that replay cleanly; five deviation kinds — undocumented transition, unknown state, unexpected entry, unexpected exit, dead transition — each counted and severity-ranked
  • Disallowed transitions turn red on the discovered lifecycle; a deviation names the cases behind it; Re-check now re-runs it against a different reference without re-import

Object-centric (OCEL)

  • One lifecycle per object type, kept together as one study; a Domain Diagram of the object model, associations weighted by interaction, dashed where two types work together undeclared
The workbench

Insights, and the slice every panel reads

The Insights workbench has eleven tabs — 📋 Activities, 🔥 Insights (the heat map), 🔀 Variants, 🎞 Cases, 🎯 Outcomes, ⌛ Between steps, ⚖ Deviations, 👥 Teams, 📈 Compare, 🤖 Automation, ⬇ Export — and one filter bar above them all. Slice by date (drag across the throughput chart), by team, or by any kept column; every tab re-reads the slice through one seam, the rebuild is exact, and every figure declares whether it is the whole run, this slice, or an estimate. Any tab expands to full screen. Explain narrates the computed figures — with AI, or deterministically without it.

Keeping it live

Sources, series and alerts

Live sources

  • Webhook (push): your system POSTs events to the ingest URL with an X-Api-Key shown once at creation
  • Blob (folder): an Azure Blob container SAS URL, polled; SharePoint (folder): picked from your tenant, refreshed manually
  • Refresh rebuilds the run in place — discovery, lifecycle and conformance re-run on the diagrams you already have; polling can be switched on or off

Series

  • Every refresh keeps a snapshot; a manual run can Snapshot too. Snapshots are linked as a series (parentRunId)
  • Compare reads the series: which steps moved, deviations that appeared and went away, conformance over the series — and refuses two runs whose vocabularies do not overlap
  • Freeze a dated run for the Compliance trend feeds the org-wide Compliance Monitoring console

Alerts

  • Rules on fitness, volume and silence, judged against the series; the source that stopped sending is raised first, because silence otherwise reads as a clean bill of health
  • Sent by email on the schedule and shown in Compare as What would be raised right now — produced by the same functions, so they cannot disagree
Where it goes

Twin, governance, automation, export

Simulate a digital twin

  • ▶ Calibrate & simulate: durations fitted per activity (fixed, triangular or a right-skewed shape as the timings warrant), arrivals from case starts, gateway odds from observed frequencies, a team per resource sized by concurrent cases, a calendar from when work happened — written onto the discovered BPMN, a study with an As-mined baseline created, the Simulator opened
  • Does the model match reality? compares the twin’s flow-time distribution with the held-back cases; a refreshed run marks its twin stale

Governance

  • Control ids on events become expected / applied / bypassed per control, shown against the control in Risk & Controls; a control can also name the conformance deviation it guards

Automation (task logs)

  • A task log — UI steps inside one job — gets an automation score and verdict, ping-pong and rework counts, hours automatable (the seconds-per-step assumption is editable), ranked candidate routines, an RPA spec .md and an SOP (.docx) / SOP (PDF)

Export

  • The analysis as Word (.docx), Excel (.xlsx) or PDF; the log itself as XES or OCEL; a run captured as a catalog example (admin)
Part two · How it does it

Before any of them: getting a run

Start with
  1. An export of events from the system that runs the process: at least a case id, an activity and a timestamp per row. A state column and a resource column make conformance and teams possible; keep them if you have them.
  2. A project to hold the run. Open ⛏ Diagramatix Miner from the project.
Build
  1. Import an event log → upload the file. If it is a wide export, accept the offer to unpivot it. If several systems cover the same cases, import the first, Add this export to a merge, then load the next; add an Id crosswalk if their ids differ.
  2. Map the columns: Case ID, Activity, Timestamp are required; add State, Resource, Control ID where present; tick any other column you will want to slice by; tick mask on anything sensitive.
  3. Read the verification panel — usable rows, dropped rows, the parsed date range. Open the full log view if anything looks wrong.
  4. If a twin is in prospect, set Hold back the most recent share now; it cannot be added later without re-importing.
  5. Import. The run appears under Imports with its cases, events, activities, states and variants.
  6. If the log lacks a state or a team column, fill them from the project’s own models: the activity→state table from a State Machine, the activity→team table from the BPMN’s lanes.
Then
  1. ⚙ Discover process and ⚙ Discover state machine under the run, and the 🔥 Insights workbench is underneath. Every guide below assumes this state.
The guides

What people use it for, step by step

1 · What does our process actually look like?

Aim: a BPMN diagram of every path people really took — usually not the one on the wall.

  1. Under Discover the process leave Detail at every path and press ⚙ Discover process.
  2. Open discovered diagram →. It is an ordinary diagram: rename, tidy, export, simulate. Re-discover at any detail level and it refreshes the same diagram.
  3. Drag Detail right to hide the rarest paths and see the dominant flow; the connector labels say how often each step was taken.
  4. Want a cleaner reading for a slide? AI-curate produces one as a separate diagram; the faithful mirror stays.

2 · How many different ways is it being run?

Aim: the distinct variants, ranked, and how few of them cover most of the work.

  1. 🔀 Variants: every distinct sequence, most common first, with its cumulative share. Read where the cumulative share passes 80% — that is how many paths matter.
  2. Click a variant to light its path on the model; tick two to see exactly what differs between them.
  3. Slice by a kept column (region, product) to see whether the long tail belongs to one part of the business.

3 · Where does the time go?

Aim: the heat map — the brightest box is where the hours are, not where the noise is.

  1. 🔥 Insights. Colour by total time for where the hours are, by average time in step for where each case waits, by frequency for where the volume is.
  2. Turn on the mined time and team under each task so the numbers sit on the picture; expand to full screen for the room.
  3. Then ⌛ Between steps — usually more of the elapsed time is on the arrows than in the boxes (guide 24).

4 · Which step is the bottleneck?

Aim: steps ranked by total time consumed, with the median time in each.

  1. 📋 Activities: one row per step with cases, occurrences, median and total time. Sort by total time; the top row is the bottleneck by hours, the top by median is the slow step per case — they are often different.
  2. An amber flag on a step means more than one team does it; open the split (guide 15).
  3. To act on it, guide 29 (Next steps) or hand it to the Simulator (guide 14).

5 · Are we doing it the way we said?

Aim: a fitness percentage — the share of cases that replay cleanly against your reference.

Start with
  1. A log with a state column, and a reference State Machine of the entity’s lifecycle. No reference yet? Under Conformance vs the reference press Create draft reference: it scaffolds one from the mined lifecycle; expect near-perfect fitness at first, then edit it into the rulebook you actually publish.
Build and read
  1. Pick the reference from the list (only state machines describing this entity are offered) and press ✓ Check conformance.
  2. Read fitness and the deviation table beneath it, ranked by cases affected.
  3. Swap in a stricter reference and check again: the fitness drop and the new top deviation are exactly which rule is broken, and how often.

6 · What exactly is going wrong?

Aim: each deviation named and counted — undocumented moves, unexpected entries and exits, states that should not exist.

  1. After guide 5, ⚖ Deviations: every deviation with its kind, count and severity.
  2. Click one to see the cases behind it (guide 23). A run checked before attribution existed says unattributed rather than showing an empty list.
  3. Slice the run (date, team) and the deviation counts restate themselves for the slice.

7 · Which paths should not be possible?

Aim: the discovered lifecycle with every disallowed transition drawn in red.

  1. After guide 5, Open state machine → under the discovered lifecycle: transitions the reference forbids are red; each carries its case count.
  2. A red transition with many cases is a policy the business has quietly changed; one with few is an error path. Both go on the same list, but they are different conversations.

8 · Do our controls actually operate?

Aim: per control — expected, applied, bypassed — measured from the log, not asserted.

Start with
  1. A log whose events carry control ids (map the Control ID column), or controls in Risk & Controls that each name the conformance deviation they guard.
Build and read
  1. Import with Control ID mapped; the governance aggregates are mined on import.
  2. Open the project’s Risk & Controls console: each control shows applied ÷ expected, or bypassed in N of M cases where it guards a deviation.
  3. Export the Risk-Control Matrix — the Control Register sheet carries the operating effectiveness.

9 · Is compliance improving or slipping?

Aim: control effectiveness over time across every project, and by APQC category.

  1. Each period, import (or refresh) the log and press Freeze a dated run for the Compliance trend on the run. A throwaway run is left unfrozen so testing never pollutes the trend.
  2. Open Compliance Monitoring from the organisation: the trend per control, per project, per APQC category.
  3. For one process rather than the organisation, guide 26 (Compare) gives conformance over the series.

10 · Are we meeting the SLA?

Aim: the on-time / late split at whatever turnaround you promise.

  1. 🎯 Outcomes. Set Case SLA — a case is late when its cycle time exceeds it. The late rate appears at once and is persisted with the run.
  2. Slice by team or period to see who is missing it.

11 · Why are cases late?

Aim: the steps and the paths over-represented in late cases, with the size of the effect.

  1. After guide 10, the same tab: What drives late cases — steps by lift among late cases — and Variants most over-represented in late cases.
  2. Click an over-represented variant to see its path; then ⌛ Between steps to find which gap on that path is the one.

12 · Which cases were the worst?

Aim: every case ranked by cycle time, down to the individual sequence of steps it took.

  1. 🎞 Cases, sorted by cycle time. Filter to one variant if you want the worst of a kind.
  2. Click a case: its path lights on the model and its timeline shows every step with the time between them.
  3. Export the case index as CSV for anyone who wants to check it.

13 · Can you show me rather than tell me?

Aim: a replay of real work flowing through the discovered process, weighted by how often each path happened.

  1. 🎞 Cases → the live replay: one runner per sampled variant over the discovered model, weighted by frequency. Expand it for the room.
  2. For a what-if rather than a replay, calibrate a twin (guide 14) and use the Simulator’s replay with the Operator.

14 · What would fixing it be worth?

Aim: a calibrated simulation — real durations, arrival rates, branch splits, teams and working hours, straight from the log.

Start with
  1. A discovered process (guide 1) and, for a testable twin, a hold-back set at import.
Build and read
  1. Under Simulate a digital twin press ▶ Calibrate & simulate. The fitted numbers are written onto the discovered BPMN, a study with an As-mined baseline is created, and the Simulator opens on it.
  2. Run the baseline; then follow the Simulator’s technical guides — a to-be scenario, Compare, the significance verdict, the business case with its payback month.
  3. Come back to Does the model match reality? to see the twin against the held-back cases before anyone quotes it.

15 · Who is doing what?

Aim: the team behind each step, and where a step is done by more than one team.

  1. Map Resource at import (or fill teams from the BPMN’s lanes).
  2. 📋 Activities shows the dominant team per step; an amber flag opens the split when more than one team does it. The dominant-team map says how many multi-team activities make it a guess.
  3. 👥 Teams for the handover map (guide 27).

16 · Is this job worth automating?

Aim: an automation score, the hours it would save, and the ranked candidate routines behind it.

Start with
  1. A task log — the UI steps inside one job, one row per step with the application and the action — imported like any other log. The built-in Enter Invoice example shows the shape.
Build and read
  1. 🤖 Automation: the score and verdict, Est. time automatable, and Candidate routines ranked.
  2. The seconds-per-step assumption behind the hours is editable; change it and the ROI restates.

17 · How is this task actually performed?

Aim: the real step-by-step routine as an RPA specification or an SOP — written from observed behaviour, not from memory.

  1. In 🤖 Automation pick the strongest candidate routine.
  2. RPA spec .md for the build team; SOP (.docx) or SOP (PDF) for the people — a styled Word document produced server-side like every other document in the product.

18 · Where does the person waste effort?

Aim: app ping-pong bounces and the steps that get redone.

  1. On a task log, 🤖 Automation → Passed back and forth (application ping-pong) and Rework — repeated work steps.
  2. On an ordinary business log the same rework reading is under 👥 Teams (guide 27) — ping-pong is a task-log measure and reads zero elsewhere, by design.

19 · How do our entities relate?

Aim: an object model mined from an OCEL log, with a lifecycle for every object type.

  1. Import an OCEL 2.0 log. Each object type becomes its own entity run inside one study; select an object type to work on its lifecycle.
  2. Open the object model (Domain Diagram) →: associations weighted by how strongly the types interact, dashed where two types work together but nobody declared a relationship.

20 · Is this still true today?

Aim: a live source that keeps the run, the diagrams and the conformance check current on their own.

Start with
  1. A mined run, and one of: a system that can POST events; an Azure Blob container the system drops files into; a SharePoint folder.
Build and read
  1. Live sources → add a source: Webhook (push) gives an ingest URL and an X-Api-Key shown once (copy it now; Copy curl example shows the call); Blob (folder) takes a SAS URL; SharePoint (folder) opens the picker.
  2. Attach the source to the run. New events rebuild it in place; polling can be toggled; SharePoint refreshes on Refresh.
  3. Every refresh keeps a snapshot — that is the series guides 26 and 28 read.

21 · Can I hand this to my manager?

Aim: the full analysis as Word, Excel or PDF, and a plain-English summary of what it found.

  1. ⬇ Export → Word (.docx), Excel (.xlsx) or PDF: summary, bottlenecks, variant Pareto, outcomes. An active slice is exported as the slice, and the summary restates itself for it.
  2. Explain for the narrative — the computed figures in prose, never instead of them; it works without AI.

22 · Can our own analysts check it?

Aim: the log back out as XES or OCEL, for ProM, Celonis, Disco, Apromore or Signavio.

  1. ⬇ Export → Export log: XES (IEEE 1849) or OCEL 2.0 JSON. Masked columns stay masked.

23 · Which cases caused this deviation?

Aim: the list behind every deviation, each with its own timeline; the whole index exports as CSV.

  1. ⚖ Deviations → click the deviation. The cases that produced it are listed; click one for its timeline on the model.
  2. Older run with no attribution? Re-check now — it gains the case list without a re-import, because the raw events were kept.
  3. Export the index as CSV to hand the fourteen cases to the person who owns them.

24 · Is the delay in the steps, or between them?

Aim: transitions ranked by the elapsed time they account for, drawn on the arrows.

  1. ⌛ Between steps: every transition with its median gap, share of the run, and total waiting; the arrows on the model carry the median and a thickness.
  2. The table is not split into in-step and between-step time, on purpose: one timestamp per event means the same milliseconds would be counted twice.
  3. The top row is the queue to fix; guide 14 to test the fix.

25 · Just this team, just this quarter?

Aim: slice the run — exactly — with every figure declaring what it covers.

  1. Above the tabs: drag across the throughput chart to narrow the dates (click once to clear); pick a team; pick a value of any column you kept at import.
  2. Every tab re-reads the slice. A figure says whole run, this slice or estimated (a strided index above fifty thousand cases) — quote it with its label.
  3. Discovery from a slice makes a diagram named after the slice; the run’s own model is untouched.

26 · What changed since last month?

Aim: two runs of the same process side by side as a linked series — and a refusal when they are not the same process.

Start with
  1. Two runs of the same process: snapshots of a live run, or last month’s manual run and this month’s imported into the same series.
Build and read
  1. 📈 Compare → Compare this run against an earlier one.
  2. Read Which steps moved, Deviations that appeared and went away, Conformance over the series, and the volume.
  3. These two runs are not comparable means their activity vocabularies do not overlap — a different process, or a renamed one — and the refusal is the finding.

27 · Who hands work to whom?

Aim: the handover map, and who does the same thing three times.

  1. Map Resource at import; the per-event resources are what the map is built from.
  2. 👥 Teams: the handover map between teams, the cross-system hand-off measured at a merge join, and Done more than once — rework by step and team on an ordinary business log.
  3. A team that hands work to itself three times is a loop nobody drew; guide 1’s discovered diagram will show it.

28 · Has the feed gone quiet?

Aim: alerts on fitness, volume and silence — the source that stopped sending, first.

Start with
  1. A live source (guide 20) with at least a few snapshots, so the rules have a series to judge against.
Build and read
  1. 📈 Compare → What would be raised right now: the alert rules’ verdict on this run, asked now rather than on the schedule. Nothing would be raised is a real answer.
  2. On the schedule the same rules send the alert email. Silence — a source that stopped sending — is raised first, because otherwise it reads as a clean bill of health.

29 · What should we do first?

Aim: ranked advice with its evidence and a button — or an honest “nothing stands out”.

  1. What to do next under the run: findings ranked, each with the evidence and the action — open the step, slice to the cases, calibrate a twin.
  2. It will not advise from an approximation (an estimated slice) and it can say nothing stands out — a perfectly even process is not a bottleneck.
  3. The optional narration sees only the ranked findings, never the raw log.
