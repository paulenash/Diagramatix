What the Simulator does, and what it should do next

A read of the Simulator as it stands from the user’s side of the screen — what it can be asked to do, the questions it already answers, and the eight additions that would make it useful to a department trying to improve how it works, rather than to an analyst trying to model one.

7 September 2026 Read from the shipped code, not the roadmap Companion to “The Simulator”, the external summary
Capability

What it does today

A discrete-event engine sitting directly on the BPMN a user has already drawn. There is no separate model to build and keep in step: the diagram is the model, and the simulation parameters live on the elements.

That single decision shapes everything below. Every capability here is reachable from a process someone drew for a different reason.

Building the model

Parameters on the diagram

  • Cycle, wait and setup times per element as five distributions — fixed, uniform, triangular, truncated normal, exponential
  • Arrival patterns on start events
  • Branch percentages on gateways, or expressions over case data
  • A Simulation Data panel showing every element’s numbers at once, editable inline, with the gaps visible

Teams and calendars

  • Teams as shared resource pools: capacity, cost per hour, efficiency
  • Working calendars — weekly shift patterns per team, operating hours per arrival source, arrival-rate multipliers by window
  • Organisation-level master teams a project adopts as its own copy
  • Team names repaired to match swim-lane labels exactly

Getting to a runnable state

  • Fill missing — arrival rate, cycle times, a team per lane, an even branch split; never overwrites what a person entered
  • Use diagram values — pull documented cycle times into the simulation
  • A readiness check on every run, separating “this will mislead you” from “a default will be assumed”
  • Filled values render differently, so a derived number never passes for a measured one

Running it

The engine

  • Tokens seize team capacity, so queues form and waiting is measured rather than assumed
  • Full BPMN behaviour: subprocesses, standard loops, sequential and parallel multi-instance, AND/OR joins, default flows
  • Boundary events racing an activity’s cycle time — interrupting and non-interrupting, timer, message, signal, conditional, escalation
  • Event subprocesses and compensation handlers
  • Timers that count working time, not elapsed time

Scale and repeatability

  • Monte-Carlo replications from a master seed — the same seed gives the same answer, always
  • Warm-up period discarded from the statistics
  • Linked subprocesses spliced in, so a portfolio runs as one network sharing its team pools — contention between processes is modelled, not ignored

Scenarios

  • A study is a set of root processes; a scenario is a run configuration laid over it
  • Scenarios store only what differs from the baseline, so a what-if is cheap
  • Planned interventions on the clock: change a capacity at hour nine, cut it for four hours, multiply arrivals, re-weight a branch, inject a backlog, take a team out entirely

Seeing the answer

Numbers

  • Flow time as mean, p5, p50, p95, with the run-to-run wobble reported separately from the case-to-case spread
  • A case-level distribution with a histogram — the typical case and the near-worst case, not just the average
  • Team utilisation, a ranked bottleneck list, busiest elements, queue lengths
  • Cost per team from busy hours × rate

Pictures

  • Heatmap over the diagram itself — each task tinted by its wait, hottest is the bottleneck. Heat inside a collapsed subprocess rolls up onto its box
  • Live replay — tokens flowing through the process, visibly stacking where the queue is
  • Token trace table — one row per case, one column per element, time spent in each, with filters and CSV out

Comparing and keeping

  • Run history — name a run and it is kept; unnamed runs are transient
  • Any two runs side by side with per-metric deltas
  • AI assessment where every figure is computed first and handed to the model, so the prose reads naturally but cannot invent a statistic

The Operator console

The most distinctive thing in the Simulator, and the hardest to put on a feature list. During a replay you can stop at the current instant, add capacity or inject work, and fork the timeline: the run continues from that moment with an identical past and a different future. It is the difference between reading a result and arguing with one.

Getting models in and out

Standards

  • BPSim XML (OMG/WfMC) export and import — times, arrivals, teams and units, branch probabilities and source calendars round-trip

Whole simulations

  • Export or import a complete simulation as one file: diagrams, team library, calendars, study and scenarios
  • A gallery of worked examples to adopt into your own project and take apart

From real event logs

  • Process Mining builds a digital twin: mined cycle-time distributions, the real arrival rate, branch probabilities from observed frequencies, teams, and a calendar derived from when work actually happened

Worth naming

Two of these are unusual in a tool at this price point. Shared resource pools across a portfolio means the simulator can show one process starving another — the failure mode most departments actually live with, and the one a single-process tool cannot see. And working calendars turn the commonest complaint in back-office work (“a two-hour job takes two days”) from a mystery into a measured quantity.

Extensions

What a department needs that isn’t there yet

The gap is not in the engine. The engine is more capable than most departments will ever need. The gap is between a correct simulation and a decision someone will sign off.

Each entry says what it is, why a department needs it, and whether it extends machinery that already exists or is genuinely new. They are in the order I would build them.

Suggested next steps, from the runs already done

After two or three runs the session holds something nobody is using: a record of what was tried and what it did. Read the current session’s runs and the saved history for the same processes, compute what changed between them, and produce a short ranked list of what to try next — “capacity on Assessment is where every improvement so far came from, and it has not been taken past six”, “three runs varied the arrival rate and none moved p95, so that is not your constraint”, “no scenario has yet tested the Monday backlog you injected once by hand”.

A simulator answers the question you ask it. This is the first feature that would help someone ask a better one — and it turns run history from an archive into an argument about where to look next.

Extends what exists High value Feasible now

A business case, not a utilisation chart

Cost exists per team, from busy hours × rate. What a department has to produce is a different shape: cost per case today, cost per case after, the annual difference, the one-off cost of getting there, and the month it pays back. Add cost of waiting and cost of rework alongside cost of doing, and generate the whole thing as a document — the machinery that writes SOPs to Word is already in the building.

No department head approves a change because a team is at 94% utilisation. They approve it because of a number with a currency symbol and a date.

Extends what exists High value

Tell them when a difference is real

The Simulator already separates run-to-run variation from case-to-case spread, which is more statistical honesty than most tools offer. But it stops short of the verdict: when two scenarios are compared, say plainly whether the difference is larger than the noise, and if it is not, say how many more replications would settle it — then offer to run them.

Someone will otherwise present a 4% improvement that is entirely sampling noise, and be found out by the first person who reruns it.

Extends what exists High value

Sweep a number instead of guessing at it

“How many people do we need?” is answered today by creating a scenario, running it, and repeating. Let one parameter be swept across a range — team size 1 to 12, arrival rate ±50% — and chart the response. The interesting feature of that curve is the knee: the point where one more person stops buying much.

The answer to a staffing question is a curve, not a number, and the curve is what stops the conversation coming round again in six months.

Extends what exists High value

Priorities and queue discipline

Every queue in the engine is first-in, first-out. Real departments are not: urgent cases jump, complaints have a clock, a segment has its own service level, and someone is always expediting. Add a priority on a case and a discipline on a team — FIFO, priority, shortest-first — and report the service level per segment rather than pooled.

A pooled p95 can look healthy while the segment that matters most misses its target entirely. This is the commonest way a simulation flatters a process.

New capability High value

Does this model match reality?

The mining twin builds a simulation from a real event log. The obvious next step closes the loop: hold back part of the log, run the model, and compare the simulated flow-time distribution against the observed one. Report the agreement as a figure and show the two distributions overlaid.

Every simulation is asked “how do we know this is right?” Today the answer is judgement. It could be a number — and for a department presenting to a finance director, that is the difference between a model and a spreadsheet with better graphics.

Extends what exists High value

People who can do more than one job

A task draws on one team, and a team is a pool of interchangeable units. That is a poor fit for a department where three people can handle assessments, one of them also handles appeals, and the manager covers both when it gets bad. Skills — an eligibility set per task and a preference order — would model that.

Cross-skilling is one of the cheapest process improvements available, and the Simulator cannot currently represent it, let alone quantify what it is worth.

New capability Medium value

Which assumption is load-bearing?

A model has thirty numbers in it and most of them do not matter. Vary each in turn and rank them by how much the answer moves — the standard tornado chart. It says where to spend effort on better data, and where a rough guess is perfectly safe.

It also disarms the meeting-room objection “but you guessed that number”: yes, and here is the evidence that it makes no difference.

Extends what exists Medium value

Smaller things, still worth doing

  1. 01 Rework and first-pass yield as a named parameter. Loops can already model rework, but nobody thinks of it that way. Ask for “what proportion comes back?” and report the cost of rework as its own line.
  2. 02 Holidays and absence. Calendars repeat weekly. A department’s year has bank holidays, a Christmas shutdown, and a summer when a third of the team is away.
  3. 03 Batching and cut-off times. Back-office work is full of “posted at 4pm” and “processed in batches of 50”, and both change queueing behaviour completely.
  4. 04 A named baseline and a trend. Pin one run as the baseline and chart the headline metrics across every run since, so improvement over months is visible rather than reconstructed from memory.
  5. 05 “What if we automate this task?” as one click. Task Mining already scores tasks for automation potential. Wiring that to a scenario which sets the task’s time near zero and drops its resource demand turns a score into a quantified saving.
  6. 06 Warm-up chosen for the user. The engine discards a warm-up period the user has to pick. Detect when the system reaches steady state and suggest it.
Feasibility

Suggested next steps: how it would work

Short answer: yes, and most of it is already built. The pattern this needs — compute every figure deterministically, hand the model only those figures — is the pattern the As-is / To-be assessment already uses.

The data exists too. Every run persists its configuration, its network and its full metrics, keyed to a scenario; named runs are kept indefinitely. The history the feature would read is sitting in the database being used for nothing but display.

1 Gather. Every run of every scenario in this study — the ones from this session and the saved history — plus the runs of any process that appears in more than one study.
2 Diff, deterministically. For each pair of runs: what changed in the configuration, and what changed in the outcome. Which levers have been pulled, over what range, and what each was worth. This is the whole trick — it is arithmetic, not judgement, and it is testable.
3 Find the gaps. Which levers have never been tried. Which were tried once and abandoned. Which produced a difference inside the noise. Which bottleneck has been top of the ranking in every run and never addressed.
4 Hand the model the facts, not the runs. A structured brief of maybe forty numbers, with the same rule the existing assessment uses: the model writes the prose and the ordering, and cannot state a figure it was not given.
5 Make each suggestion actionable. Every item names the scenario it would create and the parameter it would change — so “try eight assessors” is a button, not a homework assignment.
The one thing to get right

The model must never see raw runs and be asked to spot the pattern. It would find one whether or not it exists, and a fabricated trend in a document that goes to a finance director is the worst possible failure for this feature. Every claim in the output must trace to a number computed in step 2 — which also means the suggestions can be unit-tested without an AI call at all.

The honest limitation: with only one or two runs there is nothing to say, and the feature should say so rather than inventing advice. It earns its place from about the third run onward, which is also the point at which someone stops remembering what they have already tried.

In short

The engine is ahead of the argument

The Simulator can already model things most departments will never need — compensation handlers, non-interrupting boundary events racing a service time, parallel multi-instance bodies. What it cannot yet do is hand someone the four things they need to walk into a meeting: a cost with a date on it, a statement that the difference is real, a curve rather than a point, and evidence that the model resembles reality.

Three of those four extend machinery that already exists — and so does the fifth thing, the one that would tell someone what to try next. That is the work I would do first.
